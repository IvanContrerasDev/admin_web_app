## Problema

El contrato actual entrega refresh en JSON y `/auth/refresh` lo recibe en body. La opción web aprobada necesita cookie HttpOnly emitida por backend, access solo en memoria, restauración de usuario y rotación concurrente segura. El cuerpo de logout no identifica claramente qué refresh revocar. Un frontend no puede crear por JavaScript una cookie HttpOnly ni validar sesión decodificando claims.

## Cambio propuesto

**Propuesta pendiente: no reemplaza el transporte vigente ni autoriza a generar clientes/mocks de auth.** Para no alterar mobile, se propone extender el flujo ADMIN existente en lugar de cambiar su body MOBILE:

- `POST /auth/login`: añadir `rememberSession?: boolean` solo con `client=ADMIN`; backend guarda la elección en el challenge. Respuesta 202 existente; ningún token antes del segundo factor.
- `POST /auth/login/2fa/verify`: misma entrada vigente. Respuesta web candidata sin refresh en JSON; backend emite cookie. Vincular el challenge al inicio web y validar origen también en login/2FA para evitar login CSRF.
- `GET /auth/web/csrf`: ruta nueva, emite/recupera protección CSRF sin autenticar por sí sola. Respuesta `{ data: { csrfToken } }`, `Cache-Control: no-store`. Debe servir para bootstrap y vincular el token a sesión o contexto preauth. No abre una sesión autenticada.
- `GET /auth/web/session`: ruta nueva, cookie refresh como credencial; devuelve usuario autorizado, vencimiento absoluto y estado de recordar sesión. No rota y no devuelve access. Backend comprueba que cookie sigue activa/no revocada y rol permitido.
- `POST /auth/web/refresh`: ruta nueva, `{}` y cookie; devuelve access y usuario actuales, rota cookie, aplica CSRF. No recibe refresh en JSON.
- `POST /auth/web/logout`: ruta nueva, `{}` y cookie; revoca la sesión/cadena correspondiente e invalida cookie con mismos atributos. 204, incluso si ya no es válida, sin exigir access vigente. No revoca sesiones de otros dispositivos por accidente.
- Mobile conserva `/auth/otp/verify`, `/auth/refresh` y su almacenamiento seguro, sin cambios. Cualquier uso adicional de 2FA admin fuera de web debe identificarse antes de cambiar su respuesta.

### Tipos candidatos de las ampliaciones

```ts
interface WebLoginCandidate {
  identifier: string;
  password: string;
  client: "ADMIN";
  rememberSession: boolean;
}
interface AuthUserCandidate {
  id: string;
  firstName: string;
  lastName: string;
  email: string;
  employeeId: string;
  role: "ADMIN" | "SUPER_ADMIN";
}
interface WebSessionCandidate {
  user: AuthUserCandidate;
  sessionExpiresAt: string;
  rememberSession: boolean;
}
interface WebSessionResponseCandidate { data: WebSessionCandidate }
interface WebTokenResponseCandidate {
  data: WebSessionCandidate & {
    tokens: { accessToken: string; expiresIn: number };
  };
}
interface WebCsrfResponseCandidate { data: { csrfToken: string } }
```

Login: `{"identifier":"admin@example.test","password":"<entrada efímera>","client":"ADMIN","rememberSession":true}`. La contraseña es ilustrativa, no fixture de credenciales reutilizable. 2FA/refresh responden con el tipo candidato anterior, `expiresIn=1800`, sin clave `refreshToken`. `sessionExpiresAt` UTC representa el límite absoluto inicial, no se reinicia al rotar. 401 de sesión/refresh elimina estado local y dirige a login; nunca convierte OTP inválido en intento de refresh.

### Cookies, CSRF y despliegue por acordar

- Cookie candidata `__Host-gdes-refresh`, Secure, HttpOnly, Path=/, sin Domain, emitida en el host API. `SameSite=Lax` para despliegue same-site; cross-site solo tras aprobación: `SameSite=None; Secure` no evita el bloqueo de cookies de terceros en navegadores/iframes.
- Recordar: Max-Age igual al tiempo restante hasta el máximo absoluto de siete días. Sin recordar: cookie de sesión, sin Max-Age/Expires, pero mismo vencimiento backend. Restauración de pestañas del navegador no garantiza borrado al cerrarlo; no prometerlo.
- Preferir dominios same-site; probar en pestaña superior cuando el iframe bloquea cookies, sin desactivar seguridad ni caer a tokens persistentes.
- CORS: allowlist exacta de orígenes, credenciales habilitadas, nunca `*`. CSRF: validación Origin/Referer y token vinculado al contexto/sesión enviado en `X-CSRF-Token` para POST de cookie. Confirmar mecanismo, emisión preauth y rotación del token; permitir cabecera en preflight. CORS no sustituye CSRF.
- `Cache-Control: no-store` en auth y datos de sesión, sin tokens en URL/logs/analítica. HTTPS de producción y redacción de cookies/Authorization en trazas.

### Restauración y concurrencia

1. Arranque muestra estado de verificación, sin contenido protegido. Obtener protección CSRF y consultar `/auth/web/session` con credenciales; luego renovar bajo exclusión.
2. Una promesa de refresh por pestaña; coordinación entre pestañas same-origin mediante Web Locks y BroadcastChannel. Tras adquirir el lock, comprobar si otra pestaña ya renovó y usar el access en memoria compartido mediante canal; nunca persistirlo. Backend sigue autorizando cada llamada.
3. Compartir resultado con identificador de sesión/generación aprobado, o invalidar/restaurar estado para no mezclar usuarios. La forma concreta de ese identificador todavía debe ratificarse; no añadirlo silenciosamente al DTO anterior.
4. Logout incrementa generación local, cancela requests, limpia Query/cache/usuario y avisa a otras pestañas. Un refresh anterior no puede restablecer sesión después de logout. Backend debe resolver la carrera revocación/rotación transaccionalmente.
5. Sin conectividad se cierra la vista local y se advierte que no se confirmó revocación remota; no afirmar logout remoto ni restaurar automáticamente una sesión que el usuario quiso cerrar mientras siga viva esa intención local. Estrategia durable/recuperación al recargar pendiente de seguridad, sin guardar tokens.
6. Respuesta perdida del refresh: NO repetir a ciegas el token anterior, pues el servidor revoca por reuso. Acordar mecanismo backend de recuperación/idempotencia seguro o exigir nuevo login; preferencia candidata para MVP: login nuevo ante ambigüedad. No relajar detección de reuso con ventanas inventadas.
7. Fallback para navegadores sin Web Locks/BroadcastChannel y para dos orígenes web con la misma cookie requiere decisión de seguridad; no afirmar que la coordinación same-origin cubre esos casos.

## Impacto por app

- Backend: transporte web separado para refresh/logout/bootstrap, vencimiento absoluto y CSRF; cambios de auth model solo tras aprobación.
- Admin: access en memoria y credentials include donde corresponda, guard, cancelación y limpieza; prueba real obligatoria en F-010.
- Mobile: contratos de tokens en JSON permanecen; regresiones se prueban en backend/mobile antes de propagar.

Mocks no prueban estos controles de navegador/backend.
